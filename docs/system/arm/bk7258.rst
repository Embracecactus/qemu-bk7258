BK7258 diagnostic machines (t5_board, t5ai_core, aidk_ai_toy)
==========================================================

This is a downstream, AI-assisted local experiment. It is not an upstream
QEMU contribution and must not be submitted upstream under QEMU's current
code-provenance policy. Its base is the existing fork commit
``81ce3a87737aa50716c42db8886082d12783e0a1`` (11.1.50); no upstream history
was rewritten and no stable-release compatibility is claimed.

The three machine names identify the project's physical boards. They currently
instantiate the same shared diagnostic SoC, with distinct user LED/key wiring
for the revisions below. Other board peripherals are not yet implemented.
Listing all three names does not establish complete board support.

``hw/arm/bk7258.c`` owns the shared SoC, register map, physical cores and
on-chip devices. ``hw/arm/bk7258_boards.c`` owns the machine registrations
and explicit diagnostic image/drive loading. The loader is still an explicit diagnostic handoff, not a hardware reset-ROM
implementation. Firmware partition/role policy is not part of the SoC.

Board GPIO wiring
-----------------

The three thin board classes share the SoC but connect distinct external
endpoints. These are partial board models, not complete peripheral inventories:

.. list-table:: Modeled user endpoints
   :header-rows: 1

   * - Machine
     - User LED
     - User key
     - Released contact
   * - ``t5_board``
     - P1 active-high
     - P12 active-low
     - external 10-kOhm pull-up
   * - ``t5ai_core``
     - P9 active-high
     - P29 active-low
     - external 10-kOhm pull-up
   * - ``aidk_ai_toy``
     - P40 active-high
     - P8/KEY3 active-low
     - open; firmware selects bias

The LED uses QEMU's existing ``led`` device. Green for T5/Core is a visualization
choice, not a verified component color; AIDK LED1 is labeled red in the source
schematic. AIDK P9 is the motor control, not this board's LED. Other keys,
reset-button circuits, motor, LCD, camera, audio, storage connectors and native
USB remain unconnected. T5 P1's shared UART alternative function is not wired
to the LED yet; GPIO-mode checks must not be presented as UART waveform tests.

The machine property ``user-key-pressed`` controls the ideal contact. For
example, ``-M t5ai_core,user-key-pressed=on`` starts with it held. At runtime,
QMP can set the boolean property on ``/machine``; ``user-led-on`` is read-only
and observes the connected LED device. Holding a key across a system reset
preserves the external contact while the SoC resets its GPIO configuration.
There is no key debounce, RC charging, ADC conversion, supply or contention
model. The T5 ADC_KEY input is covered only as a digital contact endpoint.

The SoC's named ``gpio-in`` lines accept 0/1 for an external level and -1 to
release the external source. A released AIDK key therefore follows the GPIO's
configured pull, rather than always reading high. Values outside -1/0/1 are
rejected without changing the pin. An un-driven, unbiased digital input reads
zero in this functional model; that is not a physical floating-voltage claim.

Implemented slice
-----------------

* Three Cortex-M33 CPUs with separate NVICs (64 inputs, three priority bits)
  and separate 16-KiB ITCM / 16-KiB DTCM. CPU0 starts; CPU1 and CPU2 are held.
* Shared 640-KiB SRAM and all four address aliases below.
* Two explicit entry modes: diagnostic ELF-backed logical XIP, or a physical
  8-MiB NOR backing with CRC-framed XIP. The modes cannot be combined. Flash
  MMIO is mapped only with the NOR backing, so an ELF-loaded ROM cannot be
  mistaken for the controller's physical byte array.
* A bounded GD25WQ64E NOR model (JEDEC C86517, an explicit part choice, not
  board identification), 32-byte controller read/program FIFO, asynchronous
  status/ID/erase commands, real protection ranges and persistent array/NV
  status. Logical XIP removes each 2-byte CRC trailer from 32-byte payloads
  and faults on bad CRC. Controller reads and secure/NS XIP share one array.
* Three functional UARTs: transmit, bounded receive queue, RX threshold, baud-derived RX-idle completion and
  TX-finish status, W1C acknowledgement, and per-CPU interrupt routing.
  Connect UART0/1/2 with the first/second/third ``-serial`` option.
* SYS core control and interrupt enable/status registers. Reset release samples
  the vector address; changing vector bits while running does not reset a CPU.
  Halt/power gates preserve CPU state. Changes run in target-CPU order.
* Native Cortex-M33 SysTick exception delivery. CPU clock remains 26 MHz.
  SYS+0x40 bits 29/30/27 gate each core's 32,000-Hz external reference.
  Gating preserves timer count; changing an unselected source is inert.
* AON watchdog key/reload/stop and timed system reset. APB watchdog clock
  gate/divider, key/reload/stop and real CP (physical CPU0) NMI delivery;
  the NMI handler, rather than the device, decides whether to reset.
* AON PMU R0/R1/R2, keyed retention commit, sleep/wake configuration readback,
  and a selectable chip ID. Default 0x24940610 is the SDK MP-I revision choice,
  not a claim that every physical board has this revision. Override with
  ``-global bk7258-aon.chip-id=...`` when using another documented revision.
* 56 digital GPIOs: active-low output enable, input/pull state, retention lock,
  edge/level IRQ55, per-pin IRQ masking and W1C. Named GPIO inputs/outputs can
  connect board devices. SYS GPIO mux registers retain configuration; alternate
  peripheral functions are not connected to physical pads yet.
* Analog-register transactions: writes become visible after a virtual 1 us
  transfer and clear the per-register busy bit at SYS+0xe8. This is a functional
  transaction latency, not measured analog settling. Writes while busy are
  rejected. The selected SDK CP/AP defconfigs disable
  CONFIG_ANA_REG_WRITE_POLL_REG_B; the alternative SYS+0x2c busy view is absent.

* CKMN measurement at 0x448a0000 (alias 0x548a0000), IRQ21: configured
  RC32K window cycles are timed against an explicit ideal 32,000-Hz ROSC
  input; digital 26 MHz reference cycles produce a latched 20-bit count.
  For example, 64 ROSC cycles take 2 ms and count 52,000 reference cycles.
  Completion is latched under masking and acknowledged W1C; reset/disable
  cancel the operation. ANA5 bit14 powers down the measured source.
  Stable-clock windows are supported. A source change invalidates an active
  window without success; software must disable/rearm. Zero windows, stopped
  clocks and overflow do not fabricate completion. Fractional reference
  cycles round down, and completion is one-shot until software rearm. These
  edge/rounding choices are explicit functional abstractions, not measured
  synchronizer timing. Clock correction/loss-detection/autoswitch dynamics,
  physical ROSC tuning, and device ID/version probes remain unsupported.

* Native MBOX0 v2 at 0x41000000 / 0x51000000: three channels partition eight
  shared slots. TID writes enqueue two opaque words and source channel; SID
  reads pop into RX latches. Full/empty/count derive from the real queues.
  Per-core secure/nonsecure bus views enforce physical channel ownership.
  Each channel drives only its own CPU's IRQ63 and SYS high mask/status bit31.
  Firmware, not QEMU, interprets shared-memory pointers, ACKs or SMP commands.
  Tests execute actual CP/CPU1/CPU2 interrupt-driven exchanges and illegal
  cross-core TID/SID operations under protection.

Diagnostic choices are deliberately explicit: UART receive capacity is 128
bytes (not a verified silicon FIFO depth), TX drains synchronously, interrupt
route masks reset to zero, CPU1 control resets to 0x2 and CPU2 to 0xa. These
reset defaults are an emulator boot contract, not measured power-on defaults.
External SysTick routes start enabled, watchdogs start disarmed, and GPIO pads
start output-disabled with pull-down. AON retained state survives warm reset;
this is not a power-loss persistence model. AON watchdog periods use the SDK
millisecond API contract, APB uses 32 kHz / {2,4,8,16}; oscillator tolerances,
undocumented invalid-key behavior and secondary reset escalation are absent.
UART idle detection uses 26 MHz/(divider+1) and 32/64/128/256 bit-times. It is
canceled on drain, RX disable and reset; IRQ status remains W1C. Flow/wake
configuration has masked readback, but enabling physical RTS/CTS or sleep-wake
signaling emits an unsupported warning. DMA, error framing and TX timing are
not modeled. SYS clock-mode and PMU power fields retain configuration only;
no PLL lock, calibration completion, rail transition or DVFS success is faked.

MBOX0 diagnostic policies for undocumented edge cases are explicit: channel
outputs combine the individual RX/error enables; disabling a channel masks
traffic/IRQ but retains queued messages. Enabled or nonempty FIFOs cannot move
or resize, and their partitions cannot overlap or exceed the eight slots.
Invalid partitions are rejected; empty/disabled SID reads return 0xf and log a
guest error without consuming data. Unauthorized TID/SID operations latch the
documented addressed-channel WRERR/RDERR; protected configuration/data writes
are unsupported bus errors because their exact silicon response is unknown.
A full destination preserves its old entries and latches sender WRFULL. An
unavailable destination is rejected with WRERR. Raw self-send is allowed; this
is not the higher-level SDK logical-channel policy. Reset clears queues and
IRQs. No physical interconnect latency or DMA-master identity is modeled; the
global qtest bus uses CPU0's view. The 0x100 aperture covers known registers,
not a measured silicon decode window.

Migration/snapshot state is unsupported and the SoC is marked unmigratable.
Unimplemented registers report through ``-d unimp`` instead of fabricating
successful device identification or completion bits.

Aliases alone do not implement the BK7258 TrustZone attribution/security
controller. ROM, PSRAM, external timers, legacy MBOX1, DMA, physical caches,
flash remap/encryption, MCUboot/OTA and physical-board devices are absent.
Wi-Fi/BT, camera, audio, codec, power and performance behavior are not modeled.

Building and running
--------------------

On a Linux host with GCC, GLib development headers, Python, Meson and Ninja::

  mkdir ../qemu-build
  cd ../qemu-build
  ../qemu-bk7258/configure --target-list=arm-softmmu \
    --without-default-features --disable-docs --disable-user \
    --disable-tools --disable-rust --enable-tcg --enable-werror
  ninja qemu-system-arm
  ./qemu-system-arm -M help

The diagnostic entry bypasses ROM and bootloaders: CPU0's vector table is at
``0x02010000``. Use an ELF linked with a valid vector there. For the trusted
bare-metal fixture maintained by the contest repository::

  printf Z | ./qemu-system-arm -M t5_board -display none -monitor none \
    -serial stdio -kernel diagnostic.elf \
    -semihosting-config enable=on,target=native -d guest_errors,unimp

Semihosting is used solely to report fixture exit status. It can expose host
files to guests: do not enable it for untrusted images. The maintained host
entry is the contest repository's ``tools/bk7258/bk7258.py qemu`` command.
Tests and fixtures remain canonical under that repository's
``tests/host/bk7258/``; firmware C is never compiled into a QEMU device.

A passing diagnostic proves CPU instruction execution, SRAM aliases,
SysTick exceptions, core release/stop/reset, private TCM, UART receive IRQ and
system reset within this slice, including a real watchdog NMI under PRIMASK.

A separate real NuttX ``aidk_ai_toy/native_nsh`` CP ELF now reaches NSH through
unchanged NuttX/SDK startup, UART, NVIC and SysTick paths. Its existing-Kconfig
profile excludes optional product peripherals; it does not patch startup to
detect QEMU. The contest CLI ``qemu native-nsh --build-manifest ...`` checks
native task listing, UART commands, a background sleeper plus foreground
progress, elapsed uptime, error handling and guest reboot. It requires a
rehashed direct-build manifest and records ELF/source identity.

QEMU's optional FPB/DWT/debug-monitor registers are unimplemented. The pinned
NuttX ``arm_enable_dbgmonitor()`` probes them because ARCH_CORTEXM33 selects
ARCH_HAVE_DEBUG. The NSH harness preserves and counts exactly those eight
startup messages, rejecting every other unknown access, including DWT cycle
counter reads. No debugger, breakpoint or performance-counter claim follows.
The restricted native NSH also passes through physical NOR XIP without the
ELF loader. The unchanged direct product CP passes Flash initialization and
next faults at unimplemented RF register 0x4980c000 (SDK rc_drv_set_rf_en).
The MCUboot-configured CP reads unimplemented AON R7A reset-cause storage
0x440001e8 before Flash. Its snapshot/POR/reset-domain semantics are not
established by the pinned SDK, whose register definition is reserved. Both
probes enter CP directly: they do not execute ROM/BL1/BL2. Known-stop tests
retain exact configuration-specific missing-device boundaries; they do not
assert successful product boot.
Production CP/AP boot, AP SMP scheduling, RPMsg software traffic, firmware
updates and hardware timing remain outside this acceptance.

Physical NOR contract
---------------------

Use an operator-owned 8-MiB raw simulation image with
``-drive if=pflash,unit=0,format=raw,file=nor.bin``. An optional second raw
512-byte sector at ``unit=1`` persists NV SR1/SR2/SR3 in its first three bytes;
the remaining bytes must be zero. Fresh delivery state is 00 00 20. Omitting
that status drive makes status process-local, not restart-persistent. Both
backends require exclusive write/resize ownership; the device flushes a
successful mutation before updating its cached array/status. Readonly backing
or host I/O failure stops the VM rather than claiming a completed write.
A failed host commit can have partially changed the host file; the NOR latches
that failure and rejects further array access, even after reset.

The entry vector remains 0x02010000, bypassing bootloaders. The contest CLI's
``qemu native-nsh --physical-nor`` builds a fresh simulation-only image from
validated finalized artifacts and layout offsets, leaves identity/calibration
areas erased, and refuses to overwrite existing NOR files. It does not create
a board-flashable production release or run a bootloader/OTA flow.

Controller operations complete after one microsecond of virtual time, solely
as an asynchronous functional boundary, not physical program/erase timing.
Reset before that deadline cancels the operation. NOR programming ANDs bits
and wraps within a 256-byte page; erases and BP/CMP protection follow the part
contract. Protected writes are no-ops. Malformed or unsupported asynchronous
operations stop the VM; unknown MMIO/command accesses fault. FIFO underflow,
overflow and writes during active transactions are rejected. XIP observes
the last committed array during a pending operation, an explicit functional
read-cache abstraction rather than SPI bus arbitration.

CRC16 uses polynomial 0x8005, initial 0xffff and big-endian trailers. Complete
erased FF frames may be read when ALL_FF_OK is enabled. Failed-read counts
saturate at 255; this counter policy is functional, not measured hardware.
Quad XIP requires QE. The direct-entry configuration enables CRC/ALL_FF_OK;
this is not a claim about silicon power-on state. Controller-managed WREN is
inferred from the SDK's no-op write-enable wrappers. Its op7 16-bit status
transaction is modeled as two separately enabled SR-byte writes; the exact
physical controller waveform is not known.

Unsupported: raw SPI framing, SFDP/UID/security/OTP, SRP1 special modes,
volatile-status enable, suspend/deep-powerdown, page-select modes, direct CPU
XIP writes, CRC-disabled mode, remap/encryption, flash performance, brownout
atomicity and migration. The canonical tests include actual file-backed
persistence and error rejection, a production-helper ASan/UBSan harness with
mocked block failures, and real Thumb-2 instruction fetch spanning an MMIO
page. The latter also covers the downstream translator record-page fix.

Independent hardware regression
-------------------------------

The downstream QEMU repository owns its model tests. They run without an
OpenVela checkout, its CLI, a firmware build, an Arm cross-compiler or a guest
image. From a clean QEMU checkout::

  mkdir build-bk7258 && cd build-bk7258
  ../configure --target-list=arm-softmmu --without-default-features \
    --disable-docs --disable-user --disable-tools --disable-rust \
    --enable-tcg --enable-werror --enable-tests
  ninja qemu-system-arm tests/qtest/bk7258-test
  ./pyvenv/bin/meson test --no-rebuild --print-errorlogs qtest-arm/bk7258-test

The registered libqtest cases cover SRAM/MMIO aliases, UART IRQ mask/W1C,
whole-system reset, watchdog keys/feed/stop/expiry, GPIO edge/level masking,
asynchronous analog cancellation, clock ratio/IRQ routing/source loss,
mailbox routing/order/full/protection/reset, and persistent NOR AND-program,
protection, erase, reset cancellation, CRC/XIP and read-only error handling.
Each hardware case runs on all three machine names. Board cases additionally
check the actual LED/key binding, wrong-pin isolation, output disable, active-low
key IRQ/W1C, held contact across reset, released contact/internal pulls and
read-only LED observation. These qtests do not execute guest CPU instructions.

These cases were adapted from the Apache-2.0 contest hardware tests at
``ffe8356bf8b0e4eeaa504b6bcfaaf529bc842b43``,
``tests/host/bk7258/test_bk7258_qemu.py``. The source attribution and license
are retained in ``tests/qtest/bk7258-test.c`` and its adjacent LICENSE file.
They are maintained here independently, not imported or executed from the
contest project. QEMU checkpatch currently rejects Apache-2.0 in its license
allowlist; this downstream adaptation preserves its actual source license
rather than relabeling it to make the lint result green.

OpenVela is an optional external firmware consumer and evidence source.
Earlier integration/firmware checks in that independent project do not serve
as this repository's core test runner. The initial qtest slice does not replace
all earlier guest-execution, sanitizer or firmware checks. Future boot tests
must identify their external firmware assets and hashes without changing the
consumer's product code or requiring its build workflow.
